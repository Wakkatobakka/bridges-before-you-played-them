J2ME / Focused case study

It passed on the host. The phone rendered zero frames.

The missing combat sounds were inside the game’s own package. Bringing them back led us into another trap: a phone build that stopped before frame one despite passing its host checks.

Some sounds worked, and I couldn’t tell whether combat was supposed to be this quiet. We went looking. The selected handset build could play audio, and the missing attack and impact sounds were sitting in its resources.

Already in the package

The audio investigation finds eight dormant PCM WAV entries beside the enabled clips. The selected 1.4.58 build loads only its first three sound slots and rejects requests used by ordinary attack and impact paths. A comparison with an original full-audio 1.4.46 variant gives those dormant requests somewhere specific to go.G03

We followed the native requests into the original sound controller. Pressing Attack wouldn’t simply trigger a punch noise from the bridge: the game still decided when an impact happened, which request was active and what priority got played.

The original behavior stays selectable, and the game’s own Sound setting still wins. Those choices matter here because this handset edition really did disable those effects. The recovery is an optional restoration of material the game already carries, rather than a new soundtrack laid over it.G03

A wrong label was hiding in plain sight

The earlier “GRAB/CYCLE” wording also turns out to be wrong. Original help text and handlers put grabbing, chests and levers on Down/8. Star and the left softkey handle weapon or magic cycling. Two useful actions had been muddled together by the bridge label.G04

We corrected the labels to follow the game’s current prompts and original grab conditions. Down still sent Down. Fire still sent Fire when the prompt became Finish. I shouldn’t have to memorize a misleading label to use the original action.

Then the phone disagrees

Then 0.1.2 came back from the phone with zero frames, zero audio starts and one fault. We weren’t even getting far enough to hear whether the combat sounds worked.G01

The loader calls getClassLoadingLock(String), a method the investigation identifies as absent from Android’s ClassLoader API. The earlier compile had resolved that base class through the desktop JDK. The host replay ran host classfiles and skipped the Android DEX installation path. It had passed the route it exercised; the phone had found the route it had not.G02

We had to separate that failure from the sound repair. A compatibility mistake in the loader had stopped the entire game before it rendered a frame. Passing the host replay hadn’t exercised the route the phone needed.

Make that failure useful

The 0.1.3 loader uses its own monitor for class lookup and definition. The new build gate compiles against Android’s actual boot-class API. The old loader now fails the check at the very method the phone complained about; the repaired one passes, and the signed DEX no longer references it.G02

With the loader repaired, the host could again run real first-level movement, grabbing and finishers, sound on/off, restoration on/off and lifecycle transitions. We also had a check that would reject the earlier loader mistake. The phone fault had shown us something the old test wasn’t looking for.G05

About these records

The inspected 0.1.3 handoff ends with phone startup, audible restored effects, touch, save/load and Omni acceptance still open. Framework audio uses a shadow; the rage-specific sound path and full campaign were not completed. Those are the endpoint of this window, not extra setbacks invented for the story.

G02 / Why a desktop compile missed an Android API failureRegression investigation

Source: God of War: Betrayal v0.1.3 / VERIFICATION.txt · selected lines 4–18

The attached SM-S938U Android 17 reports show frames=0 and NoSuchMethodError:
getClassLoadingLock(String), in OriginalGameLoader.loadClass at line 41.
The Android SDK ClassLoader API omits that desktop-JDK method. javac with only
-classpath android.jar had resolved java.lang.ClassLoader from the desktop JDK.
The prior Engine framework replay uses host classfiles and skips device DEX
installation, so its passing result never verified this failing path.

The loader now synchronizes its own monitor while looking up/defining the six
original game classes. Class selection, resolution, resource delegation and
read-only content-addressed DEX cache behavior are preserved.
BUILD_LINUX.sh requires tools/check_loader_android_api.py, compiling the loader
with Android's actual boot-class API. The unchanged v0.1.2 source fails this
check at the exact reported method; the v0.1.3 source passes. The signed APK's
bridge DEX contains no getClassLoadingLock method reference.
This is compile/API evidence, not actual Android DEX execution.

G04 / GRAB/CYCLE was a bridge-label mistakeOriginal-control investigation

Source: God of War: Betrayal v0.1.3 / CONTROL_MAPPING_CORRECTION.txt · selected lines 1–13

Native text181 says press glyph } to grab; text114 identifies } as Down/8.
Native text219 uses the same Down glyph for opening chests/pulling levers.
Native text213 assigns * or Left Soft Key to weapons/magic. Original e.g(boolean)
handles internal10 (*) and27 (LSK) identically for weapon cycling. Internal6
(Down/8) calls e.M(), the native grab/use routine. Original a.G maps Down to -2
and numeric8 to56. The old GRAB/CYCLE wording was a bridge-label error.

Original softkey draw helper e.a(Graphics,int,int) writes kU/kV, then draws the
chosen native labels from a.m/a.n UTF8 text. Observer reads those exact fields
on the worker after paint. It does not guess a label from a screenshot/state map.
Original e.M's weak soldier conditions are observed read-only, including ground,
idle/lock gates, companion exclusion, recovery timer, health, overlap and walls.
The actual replay proves contextual GRAB -> original Down -> native pose12.
