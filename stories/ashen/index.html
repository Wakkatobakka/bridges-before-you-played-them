The buttons let go. Ashen didn’t.

I thought I’d got the controls wrong. Ashen kept sliding after release, even with the movement command cleared. The trail eventually led to the clock—and a workaround for a different game.

I thought I’d messed up the controls. Ashen was running, but moving around felt like somebody had greased the floor. My description at the time was more useful than a general complaint about the D-pad:

“It feels like we have buttered socks on”

“It feels like we have buttered socks on when we're moving”Wakka · October 19, 2026 A09

Press a direction, let go, and keep sliding. We had several sensible suspects: a missed release, a held key that never cleared, or two fingers confusing the input owner. Those were all things our touch controls could get wrong.

I’d already looked beyond this build. “I legit thought I had ported the controls wrong for this,” I wrote. “So I looked it up and nope. You just fuckig slide all around lol.” The movement finding also points to an existing upstream report of slippery Ashen movement. We had a reason to look deeper than where the D-pad sat on the screen.A09A01

Getting to that question had involved a smaller, less glamorous repair first. The 0.1.3 checkpoint records a startup fix that creates Android’s window decor before asking it for the system-bar controller. The movement reports that follow have the native game and surface attached. The shooter could now run long enough to reveal its next problem.A12

The release had already arrived

In the 0.1.4 diagnostic build, we followed the input into the original game. We watched the guest key handler and sampled the player’s movement command and position after completed gameplay frames. Key-up arrived. The movement command became zero. The position kept changing. Our obvious explanation wasn’t holding up.A06

The finding records 92 retained guest key events matching the overlapping Java event log. In one uninterrupted example, the player was still moving 1.194 seconds after release. The report had caught the game receiving the instruction to stop. Sliding continued on the other side of that boundary.A01

We were past the usual sticky-button problem. A larger button or another release event wouldn’t explain movement continuing after the command was already neutral. We needed to look at what happened between the game’s updates.

A clock that counted in pairs

The runtime exposed a 64 Hz tick counter. In the affected EKA1 path, a compatibility mask cleared its lowest bit. The values still increased, but only in pairs.A02

What the mask did to successive counter values
Unmasked012345
Masked002244

Two nearby updates could therefore ask the time and get the same answer. The next read would jump by two ticks. The clock still represented roughly 64 tick units per second, but its usable resolution had become coarser. In the earlier trace, 438 of 934 retained completed-frame samples saw zero elapsed ticks—46.9 percent.A02A04A13

Ashen accepted those zero-time updates. Analysis of the original movement code found a braking routine dependent on floor contact, alongside a collision path that could be disrupted by zero elapsed time. The before trace did not record every internal flag, so the full explanation remained a supported mechanism rather than a photograph of every step. It did, however, give the trial a very specific target.A05

The extra wrinkle was where the mask had come from. The finding quotes the nearby upstream comment as describing an unverified Worms World Party workaround. A compatibility decision for another game had become relevant to why this N-Gage shooter would not stop sliding.A02

One instruction, and the floor gets its grip back

We tried bypassing that mask in the dedicated Ashen runtime. The Android change replaced one native instruction so the original counter could pass through unmasked. The game executable, movement constants, touch movement classes and original game files stayed as they were.A03A05A10

It was a narrow experiment, which made the result easy to read. The new report calls itself 0.1.5-clock-trial and announces the clock change. Of 2,816 retained frame samples, only the first stationary startup sample had zero elapsed time. All 2,815 subsequent samples advanced.A07A04A13

The observed frame-callback spacing barely changed: medians of 16.647 milliseconds before and 16.678 after. The interesting difference was what time those callbacks could see. Seven qualifying grounded releases now slowed to zero horizontal velocity in roughly 0.32–0.34 seconds. The velocity fell steadily, and the position stayed put afterward. Two of the quiet intervals lasted more than seven seconds.A04A13

That was what made this repair satisfying. We hadn’t replaced Ashen’s movement system. Giving its original code a more useful answer from the runtime clock was enough to change the braking behavior.

“Yup, it worked. I'm having it pull out the fix and what not so I can publish it. Imma call it bsp - buttered sock patch”Wakka · October 19, 2026 A09

BSP had a name. The buttered socks had finally lost their advantage.

The next runtime question.

Ashen also sent me after something much bigger. Learning how deeply these games depended on Nokia’s original platform software made me want to build an independent Nokia runtime. I’m still working on it. In the meantime, the stopgap lets me play these games while that work continues.L02

Thirteen files, still the same game

For this chapter, we compared the 13 regular game files in the original RAR with the checkpoint inventory. Their filenames, sizes and SHA-256 entries matched. The executable was the same one named in the timing finding. The patch had changed the runtime clock underneath the original Ashen.A10

There are false starts in the paperwork too. AshenFindings.txt is an Omni Devourer investigation that reached its 60-second budget without completing an experiment. Another report is recovering an earlier session and hasn’t captured its movement probe yet. When putting this story together, we kept those separate from the actual movement tests.A08A11

About these records

The finding and both diagnostic phone traces support the clock-resolution repair on the tested phone. The old trace lacks velocity and floor-contact fields; the braking mechanism combines original-code analysis with the before/after observations. Both probes add overhead, and the later APK also contains UI-kit repairs. The general EKA1 clock edit was tested inside an Ashen-only bridge; a multi-game runtime would need a scoped compatibility choice and separate regression work. This chapter ends at the documented clock trial, without claiming an upstream merge, original-hardware timing parity or a completed campaign.A05

A02 / The clock advances in pairsRuntime investigation

Source: Ashen_Movement_Timing_Finding_2026-10-19.txt · selected lines 26–55

The function computes a 64 Hz tick counter, then applies this mask for EKA1:

    static constexpr std::uint32_t TICK_MASK = ~0b1;
    ...
    if (kern->is_eka1()) {
        res &= TICK_MASK;
    }

The nearby upstream comment describes this as an unverified Worms World Party
compatibility workaround. This file was fetched from the pinned revision and
master on 2026-10-19; the two fetched files were byte-identical and both still
contained the mask. File SHA256:
c238fb67cf1bf60f2cb3d76859ef7cb5b461f9259ed7449339cf33c4174e364f

WHY THE MASK MATTERS
The mask clears the counter's least significant bit. For example:

    Raw counter:    0, 1, 2, 3, 4, 5
    Masked result:  0, 0, 2, 2, 4, 4

The underlying 64 Hz tick period is 15.625 ms. The masked counter changes only
every 31.25 ms, in increments of two. It still represents approximately 64
tick units per second: this is reduced resolution, not a clock running at
half speed. With game callbacks near 60 per second, many successive reads
produce a zero elapsed-tick delta, followed by a two-tick delta.

The original Ashen timestep calculation accepts zero elapsed time. The
pre-change phone trace showed its movement command clearing after release
while the player's position continued changing. Input release delivery was
not the cause demonstrated by that trace.

A03 / One instruction in the runtimeCompatibility trial

Source: Ashen_Movement_Timing_Finding_2026-10-19.txt · selected lines 58–76

The dedicated Ashen runtime was edited; the original game executable was unchanged. No binary is distributed here.

Leave the computed counter unmasked for Ashen:

    - res &= TICK_MASK;
    + // Ashen-only runtime: leave res unmasked.

The native time provider, timer origin, tick period and existing pause logic
were left intact. No FPS cap, time-delay setting, minimum-timestep clamp,
forced velocity reset or friction constant was changed.

ACTUAL ANDROID BINARY CHANGE
The delivered test used a reversible binary compatibility edit to the pinned
ARM64 native library; it was not a complete source rebuild of EKA2L1.
Exactly one instruction changed:

    Before: and w10, w9, #0xfffffffe
    After:  mov w10, w9

The subsequent conditional select therefore receives the unmasked counter.
This changes the EKA1 result while preserving the existing EKA2 result.

- All 120 retained Java dispatches matched guest input events.
- Median observed completed-frame callback gap: 16.678 ms.
- Seven clean high-speed grounded releases reached zero horizontal velocity
  in 321.710-342.649 ms (median 326.537 ms).
- Their velocities decreased monotonically and positions stayed fixed after

- Floor-contact state remained set through those braking sequences.
- The user's gameplay video and assessment agreed with the measured repair.

The seven release examples require: at least one second before the next
movement press, zero movement commands throughout, initial raw horizontal
speed >=45000, continuous floor contact through stopping, and the first
sample within 50 ms of the guest release. Overlapping inputs, short gaps,
airborne releases and already wall-stopped inputs are excluded. Positions
and velocities are original fixed-point integers; no metres conversion is
assumed. The histories are sampled/retained traces, not every event forever.

The four touch movement/input classes were also identical. The after build
integrated UI Kit 1.1.1's startup/dialog release repairs and extended the
read-only observer; it was not otherwise a byte-identical APK. Both probes
observed the original guest through guarded debugger hooks and added some

original-hardware timing parity and Worms regressions were not tested.

UPSTREAM IMPLEMENTATION SCOPE
The tested runtime belongs to a dedicated Ashen bridge. Removing this mask
there changes its EKA1 counter generally; the binary instruction itself is
not guarded by Ashen's UID. For a multi-game EKA2L1 release, a title-specific
compatibility option/profile for Ashen (UID 0x101FD3E9) is the appropriate
next implementation to evaluate. Preserve the Worms workaround for the game
that needs it until broader regression tests establish a safe default.
There is no claim that the same change fixes every slippery game.
