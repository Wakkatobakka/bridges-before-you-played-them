# Editorial method

## The story and the record

These chapters follow the surprise, the broken behavior and the attempt that changed it. The reader can enjoy a story without opening every receipt; the receipts make its details inspectable.

I supply the direction, constraints, phone testing and remembered experience. ChatGPT helps investigate and implement the bridges, and helped assemble this archive from the saved development record. The main narrative uses my perspective: “I” for my recollections and reactions, and “we” for the work together. Where a memory reaches beyond the surviving technical record, the chapter keeps that distinction visible.

Recorded quotations keep their original wording and context. Dialogue, laughter, reactions and scenes are not invented to fill gaps. Measurements and test limits appear where they affect the story, with longer scope notes in the receipts and one expandable endnote per chapter.

Each chapter names the version window and surviving sources it covers. Its ending describes that historical record, rather than assuming the current bridge has the same status. Current releases and installation information live with [Omni Player](https://github.com/Wakkatobakka/Omni-Player).

## Evidence types

**Phone reports** contain observed runtime counters, traces and faults from a particular session. A build header may be inherited from an earlier build; a statement in that header is not automatically a fresh test result.

**Host and build checks** establish their recorded code paths, API compatibility, resource behavior, packaging or regressions. Framework stand-ins, deferred game boot and host classfiles remain labeled as such.

**Owner feedback** describes the exact behavior and build recorded. A later candidate does not inherit a phone verdict merely because the preceding build worked.

**Checkpoint notes** preserve technical explanations and prior evidence at a particular point. Later notes can record later acceptance while leaving an earlier untested-build status intact.

**Archive comparisons** are findings derived from inspected source files. They are labeled as comparisons rather than presented as original log lines.

## Traceability

Numbered links open source-ledger exhibits. Verbatim excerpts give original source names and selected line ranges. Ellipses mark noncontiguous selections. Derived comparisons state their method. Plain-text downloads preserve the reviewed exhibits in an independently inspectable form.

Published excerpts are checked against their sources. The complete private documents stay outside the site; a hash can identify a source without distributing its bytes. Historical images carry source and capture labels, including distinctions between original phone recordings, host framebuffers and emulator windows.

## Counting and chronology

- Original filenames and internal app/runtime identifiers are preserved, including disagreements.
- Session identity and log overlap are compared before exports are counted as independent tests.
- Log events are counted once, using the full retained log rather than both preview and full-log sections.
- Version or sequence order is used where session dates are not established. Upload timestamps are not treated as test dates.
- Mixed game identities are kept separate rather than assigned to a convenient failure narrative.
- Unavailable evidence stays visibly unavailable. A failed filename search does not establish that a report never existed.

## Public and private material

The site contains reviewed prose, diagnostic excerpts, authored web code and labeled historical imagery. Complete private checkpoints, bridge implementation, shared UI-kit source or JARs, signing keys, build tools, original game packages, firmware and prepared game executables are excluded.

Published material omits private machine and installation paths, unique session/device identifiers, credentials and personal contact information. Public source ledgers do not link full private checkpoints.

Original games, translations, upstream runtimes and tools retain their own credit. This archive documents the development of the bridges; original-file sourcing and play instructions belong with Omni Player and its game guides.
